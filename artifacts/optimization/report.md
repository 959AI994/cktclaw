## 2. 瓶颈分析

### 2.1 时序瓶颈（优先级：高）
```
关键路径分析：
  ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
  │ 数据输入    │ →   │ 校验和计算  │ →   │ 结果输出    │
  │ (1 cycle)   │     │ (3 cycles)  │     │ (1 cycle)   │
  └─────────────┘     └─────────────┘     └─────────────┘
                       ↑ 瓶颈：组合逻辑深度过大
```

**根因：**
- 校验和计算路径组合逻辑过深（3 cycle 延迟）
- 导致 WNS -0.35ns 违规
- 流水线无法达到 1 cycle/byte 吞吐

### 2.2 面积瓶颈（优先级：中）
- 校验和累加器实现过于复杂
- 数据缓冲 FIFO 深度过大
- 冗余的握手逻辑

### 2.3 功能/验证瓶颈（优先级：高）
- Yosys 错误：可能是 RTL 语法或结构问题
- DUT bug：验证发现的功能缺陷
- 3 个 EDA fix_request 未关闭

### 3.2 时序优化（P1 — 关键性能）

#### [P1-1] 校验和计算流水线化
```yaml
建议: 将校验和计算拆分为 3 级流水线
当前实现:
  always_comb begin
    checksum = data_in + checksum_prev;  // 单周期组合逻辑
  end

优化实现:
  // 第1级：部分和计算
  always_ff @(posedge clk) begin
    partial_sum_1 <= data_in[7:0] + data_in[15:8];
  end
  // 第2级：累加
  always_ff @(posedge clk) begin
    partial_sum_2 <= partial_sum_1 + checksum_prev;
  end
  // 第3级：最终结果
  always_ff @(posedge clk) begin
    checksum <= partial_sum_2;
  end

预期收益:
  - WNS 改善: +0.4 ns（达到 ≥0.0）
  - 吞吐率: 1 byte/cycle（流水线化后）
  - 代价: 增加 2 cycle 延迟（可接受）
风险: 低 — 标准流水线技术
```

#### [P1-2] 优化关键路径组合逻辑
```yaml
建议: 使用并行前缀加法器替代串行加法
具体操作:
  - 替换 `checksum = data_in + checksum_prev` 为 Kogge-Stone 加法器
  - 或使用 FPGA 专用加法器原语
预期收益: 减少组合逻辑深度 30-40%
风险: 中 — 面积增加 10-15%
```

### 3.3 面积优化（P2 — 资源效率）

#### [P2-1] 优化数据缓冲 FIFO
```yaml
建议: 使用寄存器堆替代 BRAM（小深度场景）
当前: 深度 64 的 BRAM FIFO
优化: 深度 8 的寄存器 FIFO
预期收益: 减少 BRAM 使用，LUT 增加可接受
条件: 确认最大突发长度 ≤ 8
```

#### [P2-2] 精简握手逻辑
```yaml
建议: 移除冗余 valid/ready 信号
具体操作:
  - 分析数据流图，识别不需要握手的路径
  - 使用简单使能信号替代
预期收益: 减少 5-10% LUT 使用
```

### 3.4 架构级优化（P3 — 长期改进）

#### [P3-1] 引入预取机制
```yaml
建议: 在数据输入前预取下一个包
实现:
  - 添加 2 级预取缓冲
  - 当当前包处理时，预取下一包数据
预期收益: 减少流水线气泡，吞吐率提升 10-15%
风险: 低 — 标准技术
```

#### [P3-2] 动态频率调整
```yaml
建议: 根据负载动态调整时钟频率
实现:
  - 添加时钟门控
  - 低负载时降频节能
预期收益: 功耗降低 20-30%
条件: 需要时钟管理单元支持
```
